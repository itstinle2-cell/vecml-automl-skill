Survey of Recent Post-Training RL Methods for Language Models

Built locally from recent paper pages, supporting resources, and directly inspected code from cloned repositories.

Scope

This survey focuses on post-training methods that improve language-model behavior after pretraining, especially reinforcement-learning-based or preference-optimization-based methods used for reasoning, alignment, and response quality. I prioritized methods that are both conceptually important and connected to real open-source codebases that could be inspected locally.

Selected publications / artifacts

  1. Direct Preference Optimization: Your Language Model is Secretly a Reward Model (2023) — DPO
  2. DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models (2024) — GRPO framing referenced in TRL implementation
  3. ORPO: Monolithic Preference Optimization without Reference Model (2024) — represented by TRL ORPO trainer
  4. Supervised Fine-Tuning versus Reinforcement Learning: A Study of Post-Training Methods for Large Language Models (2026)
  5. OpenRLHF Technical Report / Framework Documentation (framework artifact; PPO, GRPO, REINFORCE++, DPO implementations)

Method 1: DPO

DPO is one of the most influential simplifications of RLHF-era post-training. Instead of fitting a separate reward model and then running PPO against it, DPO directly optimizes preference pairs using log-probability differences between chosen and rejected responses. In practice, this made preference post-training more accessible and easier to reproduce.

Direct code evidence from the cloned reference implementation:

def preference_loss(policy_chosen_logps: torch.FloatTensor,
                    policy_rejected_logps: torch.FloatTensor,
                    reference_chosen_logps: torch.FloatTensor,
                    reference_rejected_logps: torch.FloatTensor,
                    beta: float,
                    label_smoothing: float = 0.0,
                    ipo: bool = False,
                    reference_free: bool = False) -> Tuple[torch.FloatTensor, torch.FloatTensor, torch.FloatTensor]:
    ...
    pi_logratios = policy_chosen_logps - policy_rejected_logps
    ref_logratios = reference_chosen_logps - reference_rejected_logps
    ...
    logits = pi_logratios - ref_logratios
    ...
    losses = -F.logsigmoid(beta * logits) * (1 - label_smoothing) - F.logsigmoid(-beta * logits) * label_smoothing

That excerpt comes directly from repos/direct-preference-optimization/trainers.py. It captures the core attraction of DPO: preference optimization becomes a supervised-looking objective over policy/reference log-ratios rather than a separate reward-model-plus-policy-optimization pipeline.

Method 2: GRPO

GRPO has become highly relevant in reasoning-focused post-training because it replaces or relaxes some of the machinery of actor-critic RL with group-relative comparisons over generated candidates. This is especially attractive for domains like math reasoning, where relative quality among multiple sampled completions can be informative.

Direct code evidence from TRL’s GRPO trainer:

class GRPOTrainer(_BaseTrainer):
    """
    Trainer for the Group Relative Policy Optimization (GRPO) method. This algorithm was initially proposed in the
    paper DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models.
    """

RewardFunc = str | PreTrainedModel | Callable[..., list[float | None]]
RolloutFunc = Callable[[list[str], "GRPOTrainer"], dict[str, Any]]

This excerpt from repos/trl/trl/trainer/grpo_trainer.py shows two important practical ideas: (1) GRPO is treated as a first-class trainer rather than an ad hoc script, and (2) reward functions can be either model-based or custom callables, which makes GRPO attractive for domains with verifiable or structured rewards.

Method 3: PPO / RLHF pipelines

PPO remains the canonical RLHF-style baseline and production workhorse. Even when newer methods like DPO or GRPO get the attention, PPO-style pipelines still matter because they expose the engineering realities of rollouts, KL control, replay buffers, and distributed actor/critic coordination.

Direct code evidence from OpenRLHF:

if self.args.kl_target:
    self.kl_ctl = AdaptiveKLController(self.args.init_kl_coef, self.args.kl_target, self.args.kl_horizon)
else:
    self.kl_ctl = FixedKLController(self.args.init_kl_coef)

self.experience_maker = RemoteExperienceMaker(
    self.actor_model_group,
    self.critic_model_group,
    self.reward_model_group,
    self.reference_model_group,
    self.kl_ctl,
    self.strategy,
    tokenizer,
)

This excerpt from repos/OpenRLHF/openrlhf/trainer/ppo_trainer.py illustrates the system-level complexity that DPO tries to avoid. PPO pipelines require explicit management of KL control, rollout experiences, actor/critic/reward/reference components, and often distributed systems machinery.

Method 4: ORPO

ORPO is interesting because it keeps the preference-optimization flavor but removes the need for a separate reference model. This matters in practice because reference-model handling adds both memory cost and implementation complexity.

Direct code evidence from TRL’s ORPO trainer:

class ORPOTrainer(_BaseTrainer):
    _paper = {
        "title": "ORPO: Monolithic Preference Optimization without Reference Model",
        "id": "2403.07691",
    }

That excerpt from repos/trl/trl/experimental/orpo/orpo_trainer.py makes the method’s central claim explicit in the trainer itself: preference optimization without a reference model. Conceptually, ORPO sits in the same family as DPO-like methods that trade some RLHF complexity for simpler optimization pipelines.

Method 5: Comparative post-training studies

The most practically useful papers are often not new algorithms but comparative studies that ask when SFT is enough, when RL matters, and how gains differ across tasks. The recent paper Supervised Fine-Tuning versus Reinforcement Learning: A Study of Post-Training Methods for Large Language Models is relevant precisely because many teams are trying to decide whether RL-style post-training is worth the extra complexity.

The main gap in this area is that many public claims about “reasoning gains” still depend heavily on benchmark selection, reward design, and prompt format. Comparative studies are valuable because they can reveal where RL methods truly outperform simpler baselines and where they mostly reshuffle training signal.

Synthesis

  • PPO/RLHF offers the richest control but the heaviest engineering burden.
  • DPO made preference optimization dramatically simpler and more reproducible.
  • ORPO pushes simplification further by removing the reference model.
  • GRPO is especially attractive for reasoning tasks where relative ranking among multiple sampled outputs is informative.
  • Modern frameworks like TRL and OpenRLHF matter because they operationalize these ideas as reusable trainers rather than one-off paper code.

Future research directions

  • Better reward design for reasoning: Many authors implicitly rely on narrow verifiable rewards or benchmark-specific signals. A major gap is reward functions that capture reasoning quality beyond final-answer correctness.
  • Stability vs simplicity: DPO/ORPO-style methods are simpler than PPO, but comparative evidence is still emerging on when that simplicity leaves performance on the table.
  • Long-horizon and agentic post-training: Existing post-training pipelines are still much stronger on single-turn tasks than on multi-step tool use and long-horizon planning.
  • Replay, reflection, and curriculum: Several recent directions suggest that replay buffers, reflection rewards, and difficulty-aware curricula may be as important as the base RL algorithm.
  • Evaluation realism: The field still needs stronger evaluations that distinguish genuine reasoning improvements from reward hacking, benchmark overfitting, or verbosity artifacts.
  • Open implementations of recent methods: One persistent gap is that many recent papers have limited or no official code release, which makes rigorous comparison difficult. This is a major reproducibility bottleneck.
